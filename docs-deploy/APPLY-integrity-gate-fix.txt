رفع گیت «صحت پس از استقرار» — نیاز به یک بار اقدام دستی شما دارد
=====================================================================

تاریخ: ۲۰۲۶-۰۹-۰۴ · نسخه: v34.36.0 · مربوط به: deploy-production.yml و deploy-staging.yml


چرا این پوشه و نه خودِ .github/workflows/؟
------------------------------------------
توکن GitHub App که ايجنت با آن کار می‌کند اجازهٔ `workflows` ندارد، پس push هر
تغییری در `.github/workflows/**` از سمت گیت‌هاب رد می‌شود:

  ! [remote rejected] (refusing to allow a GitHub App to create or update
    workflow `.github/workflows/deploy-production.yml` without `workflows` permission)

این همان محدودیتی است که در `docs-deploy/deploy-staging.yml` هم از قبل مستند شده:
«ایجنت اجازه ساخت فایل workflow را در گیت‌هاب ندارد — محدودیت امنیتی گیت‌هاب».
برای همین اصلاح ورک‌فلو اینجا گذاشته شده تا **شما** با اعتبارنامهٔ خودتان اعمالش کنید.


چه چیزی خراب است؟
-----------------
گام `Post-deploy integrity check` در هر دو ورک‌فلو **هرگز نمی‌توانست سبز شود**،
کاملاً مستقل از اینکه استقرار درست انجام شده باشد یا نه.

`FILES` یک رشتهٔ «یک‌خطی با فاصله» بود:

    FILES="crm/sw.js crm/shell.js crm/client-server.js crm/key-registry.js crm/sales-domain-v2.js"
    while IFS= read -r f; do ... done <<< "$FILES"

چون `IFS` تهی است، `read` کل خط را یک‌جا می‌گیرد و حلقه **فقط یک بار** می‌چرخد،
با این مقدار در `f`:

    crm/sw.js crm/shell.js crm/client-server.js crm/key-registry.js crm/sales-domain-v2.js

نتیجه در هر تلاش:

    sha1sum: 'crm/sw.js crm/shell.js ...': No such file or directory   →  want = (تهی)
    curl: (3) URL using bad/illegal format or missing URL             →  got  = da39a3ee5e

پس `want != got` همیشه برقرار است، ۵ تلاش بی‌نتیجه می‌سوزد و گام با `exit 1`
می‌افتد. علت اینکه در صفحهٔ Actions دیده نمی‌شد: این خطوط `≠` فقط stdout هستند
و تنها `::error::` پایانی به annotation تبدیل می‌شود.

شاهد عملی: در دو اجرای مستقل — `main@4ec342e` با v34.35.0 (۹ ساعت پیش) و
`arena@7366edf` با v34.36.0 — همین گام شکست، درحالی‌که در همان دو اجرا
`verify-deploy.sh` هر ۵ فایل را «هش زنده == کامیت ✅» گزارش کرده بود. یعنی
محتوای سایت زنده درست بود و فقط حلقهٔ این گام خراب است. دلیلش هم روشن است:
`verify-deploy.sh` متغیر `BYTES_FILES` را **چندخطی** می‌سازد، پس درست حلقه می‌زند.


چه چیزی در این فایل‌ها هست؟
---------------------------
FIX-integrity-gate-FILES-multiline.patch
    پچ surgical، فقط همان دو گام در دو ورک‌فلو (۷۱ خط +، ۱۰ خط −).

deploy-production.FIXED.yml
deploy-staging.FIXED.yml
    نسخهٔ کامل و اصلاح‌شدهٔ دو ورک‌فلو — آمادهٔ کپی مستقیم.


خلاصهٔ اصلاح
------------
• `FILES` چندخطی شد (یک نام در هر خط) — همان الگوی اثبات‌شدهٔ `BYTES_FILES`.
• دانلود با `-o` در فایل موقت، تا «خطای دریافت» از «محتوای متفاوت» جدا شود.
• گارد `[ ! -f "$f" ]` و `[ -z "$f" ]` با پیام روشن.
• گزارش اندازهٔ بایت کامیت/زنده و تشخیص تفاوت پایان‌خط (`\r`) در پیام خطا،
  هم‌راستا با منطق موجود در `verify-deploy.sh`.
• در استیجینگ، `live_sw` و `live_idx` هم از همان فایل موقت خوانده می‌شوند و
  خطای `curl` دیگر با «نسخه ارجاع نمی‌دهد» اشتباه گرفته نمی‌شود.

راستی‌آزمایی انجام‌شده: با یک سرور HTTP محلی روی همین درخت کاری، نسخهٔ قدیمی در
هر دو تلاش با `want` تهی و `got=da39a3ee5e` می‌بازد؛ نسخهٔ اصلاح‌شده در تلاش اول
«✅ همهٔ فایل‌های حساس زنده == کامیت» با `exit=0` می‌دهد — برای هر دو ورک‌فلو.
YAML هر دو معتبر و `bash -n` روی اسکریپت استخراج‌شده پاک است.


چطور اعمال کنید (یکی از سه راه)
-------------------------------
راه ۱ — پچ (تمیزترین، از ریشهٔ مخزن):

    git apply docs-deploy/FIX-integrity-gate-FILES-multiline.patch
    git add .github/workflows/deploy-production.yml .github/workflows/deploy-staging.yml
    git commit -m "ci: رفع گیت صحت — FILES چندخطی شد"
    git push

راه ۲ — کپی مستقیم فایل‌های کامل:

    cp docs-deploy/deploy-production.FIXED.yml .github/workflows/deploy-production.yml
    cp docs-deploy/deploy-staging.FIXED.yml    .github/workflows/deploy-staging.yml
    git add .github/workflows/ && git commit -m "ci: رفع گیت صحت — FILES چندخطی شد" && git push

راه ۳ — ویرایش دستی در وب‌سایت گیت‌هاب (اگر دسترسی محلی ندارید):
فقط در گام `Post-deploy integrity check` هر دو ورک‌فلو، خط `FILES="..."` را به
شکل چندخطی زیر عوض کنید (بدون هیچ تورفتگی اضافه در خودِ رشته):

    FILES="crm/sw.js
    crm/shell.js
    crm/client-server.js
    crm/key-registry.js
    crm/sales-domain-v2.js"

و برای پروداکشن به‌همین ترتیب با `crm/index.html` در ابتدا و `crm/manifest.json`
در انتها. همین یک تغییر، انسداد را برمی‌دارد؛ بقیهٔ اصلاح‌ها تشخیصی‌اند.


ترتیب درست برای رسیدن به پروداکشن
----------------------------------
۱) PR #2 را merge کنید — گیت CI را سبز می‌کند (۲۰۲ PASS / ۰ FAIL). این به تنهایی
   انسداد فعلی دیپلوی پروداکشن را برمی‌دارد، چون آن اجرا در گام `CI gate`
   می‌مرد و هرگز به FTP نمی‌رسید.
۲) اصلاح ورک‌فلو را طبق بالا اعمال و push کنید. بدون این، دیپلوی پروداکشن
   آپلود می‌شود ولی در آخرین گام (`Post-deploy integrity check`) قرمز اعلام
   می‌شود — یعنی سایت درست بالا آمده ولی ورک‌فلو آن را «ناموفق» گزارش می‌کند
   و تگ نسخه و Release بک‌آپ ساخته نمی‌شوند.
۳) سپس: Actions ← Deploy to Production ← Run workflow با `confirm=DEPLOY` و `ref=main`.


یک نکتهٔ جانبی که دیدم (رفع نشد)
---------------------------------
در اجرای استیجینگ، گزارش تشخیصی این خط را چاپ کرد:

    [FTP] مسیر مقصد () با LIST/NLST خوانده نشد (مجوز یا پروتکل)

آن `()` **خالی** است، یعنی سکرت `FTP_SERVER_DIR` در استیجینگ مقدار ندارد.
چون این بررسی فقط تشخیصی است، job را نینداخت و آپلود از مسیر `FTP-Deploy-Action`
انجام شد. ولی اگر مسیر مقصد واقعاً لازم است، در
Settings → Secrets and variables → Actions مقدار آن را پر کنید.
سکرت‌های پروداکشن (`FTP_PROD_SERVER_DIR` و بقیه) را نتوانستم بررسی کنم —
توکن فعلی برای خواندن فهرست سکرت‌ها هم `403` می‌گیرد.
