# تبدیل پیشنهاد ارزی برنده به پیشنهاد ریالی — بررسی و پیاده‌سازی (US-FX2RIAL فاز ۱)

**تاریخ:** ۱۴۰۵/۰۵/۱۵ (2026-08-06) — **نسخه CRM:** v34.2.0 — **وضعیت:** پیاده‌سازی و تست شد ✅

---

## ۱) شرح سناریو (دستور کارفرما)

- یک پیشنهاد مالی **ارزی** (EUR/USD) برنده شده است.
- کارفرما (خریدار) تقاضا دارد **نسخه ریالی** همان پیشنهاد هم به او ارائه شود.
- طبق منطق موجود، **پیشنهاد برنده قفل است و تغییر نمی‌یابد** (US-141 / US-431).
- باید با **کمترین پیچیدگی** امکان تبدیل فراهم شود:
  - تاریخ نسخه ریالی به‌صورت پیش‌فرض = تاریخ پیشنهاد اولیه؛ در صورت درخواست کاربر قابل تغییر.
  - نرخ تسعیر و تاریخ از کاربر پرسیده شود.
  - آثار مالی تبدیل بررسی و در صورت نیاز منطبق شود.
- **فاز ۲:** تعمیم همین امکان به تمام پیشنهادهای ارزی، حتی غیربرنده.

## ۲) بررسی‌های انجام‌شده روی CRM (مسیرهای مرتبط)

| موضوع | فایل/محل | نتیجه بررسی |
|---|---|---|
| قفل پیشنهاد برنده | `offers.js → offerPostAwardLocked / offerSetSt` | پیشنهاد برنده read-only است؛ تغییر وضعیت/ویرایش/حذف ممنوع — نباید دست بخورد |
| ارز سند پیشنهاد | `offers-pro.js (US-182)` | فیلدهای `currency` (IRR/EUR/USD) + `fxBasis` + `fxRateRef` روی CO/TC |
| تشکیل پرونده فروش | `offers.js → autoCreateProjectFromCO` + `salesfiles.js` | فقط با «برنده» شدن CO؛ `deals.wonOffer` = سند مبنای کل فرایند بعد از برد |
| ارجاع/صدور فاکتور رسمی | `salesfiles.js → sfInvoiceRefCommit` + `rbac.js` | **همیشه از پیشنهاد برنده (`wonOffer`)**؛ فاکتور رسمی حتی برای سند ارزی **ریالی** صادر می‌شود (با `issueFxRate`) |
| صورتحساب غیررسمی | `unofficial-invoice.js` | سند ارزی را با نرخ تسعیر روز صدور به ریال نمایش/چاپ می‌کند |
| موتور سود ارزی | `fx.js` | سود پروژه از «دریافت‌های ریالی تسعیرشده» محاسبه می‌شود — نه از ارز پیشنهاد |
| آمار برد/باخت | `analyzer.js`, `reports.js`, `scoring.js`, `insights.js` | همه با `o.st === 'won' / 'lost'` روی CO می‌شمارند → نسخه همراه هرگز نباید این وضعیت‌ها را بگیرد |
| فرصت‌های فعال | `oppo.js` | درخواست‌های دارای inq برنده کلاً از لیست فرصت خارج‌اند → نسخه همراه فرصت جدید نمی‌سازد |
| یادآور انقضای پیشنهاد | `bridge.js`, `myday.js`, `offerValidState` | فقط روی `validUntil` فعال است → نسخه همراه بدون `validUntil` ساخته می‌شود |
| شماره‌گذاری رسمی | `codegen.js → ptfUnifiedCodeAsync` | شماره CO فقط از استخر سرور؛ TMP هرگز سند رسمی نمی‌شود |

## ۳) راه‌حل پیاده‌شده (فاز ۱)

**دکمه «💱 تبدیل به پیشنهاد ریالی»** در نوار «🧰 عملیات پرونده (Post-Award)» داخل کشوی پرونده فروش
(`salesfiles.js → sfDrawerHtml`) — فقط وقتی پیشنهاد برنده پرونده **ارزی** باشد و نسخه ریالی نداشته باشد.

روال کار:

1. کلیک روی دکمه → دیالوگ تبدیل باز می‌شود:
   - **نرخ تسعیر** (ریال به‌ازای هر واحد ارز) — پیش‌فرض: `fxRateRef` ثبت‌شده خود پیشنهاد، وگرنه نرخ آزاد لحظه‌ای (`_ptfFxLive`)
   - **تاریخ پیشنهاد ریالی** (شمسی) — پیش‌فرض: **تاریخ پیشنهاد اولیه** (`dateEn` پیشنهاد ارزی)؛ قابل تغییر
   - پیش‌نمایش زنده معادل ریالی (دقیقاً با همان فرمول تبدیل)
2. تایید → ماژول `offer-rial-convert.js`:
   - شماره رسمی CO از سرور رزرو می‌کند (`ptfUnifiedCodeAsync`)
   - یک **پیشنهاد همراه (Companion)** جدید می‌سازد:
     - `currency = 'IRR'`، قیمت هر ردیف = `round(قیمت ارزی × نرخ)` به ریال صحیح
     - `rialOf = <شماره پیشنهاد ارزی>` + بلوک ممیزی `fxConvert` (نرخ، مبلغ ارزی/ریالی، تاریخ، کاربر)
     - `st = 'sent'` (ارسال‌شده) — هرگز برنده/بازنده نمی‌شود
     - همان `inqNo` → خودکار در کشوی همان پرونده فروش و فهرست پیشنهادها ظاهر می‌شود
     - بدون `validUntil` (یادآور انقضا نمی‌گیرد — معامله قبلاً برنده شده است)
     - بدون `invRef / wonAt / altOf / srcToNo / coNo / marginAtClose` — این‌ها به سند اصلی متصل می‌مانند
   - در تایم‌لاین پرونده + حسابرسی (`audit`) + اعلان به نقش‌های ارشد ثبت می‌شود
3. پس از ساخت: پیشنهاد چاپ/PDF شود؟ (ریال، قالب Commercial Offer)
4. بعد از تبدیل، جای دکمه در پرونده **بج «💱 ریالی: شماره» + دکمه‌های 👁/🖨** می‌آید (تبدیل مجدد مجاز نیست — یک نسخه ریالی per پیشنهاد ارزی).

## ۴) آثار مالی — بررسی و انطباق

| اثر مالی | تحلیل | اقدام |
|---|---|---|
| پیشنهاد برنده ارزی | هیچ فیلدی تغییر نمی‌کند؛ قفل برد، `awardDocs` (سند قطعی برد) و `invRef` دست‌نخورده | بدون اقدام — طبق خواسته کارفرما |
| فاکتور رسمی | همچنان از `wonOffer` ارزی ارجاع و **ریالی** صادر می‌شود (روال موجود `rbac.js` با `issueFxRate`) | بدون اقدام — تبدیل، مسیر فاکتور را تغییر نمی‌دهد؛ سند ریالی صرفاً سند ارائه به کارفرماست |
| آمار برد/باخت (تحلیلگر/گزارش‌ها) | اگر نسخه ریالی «برنده» می‌شد، برد دوشمار و `wonOffer` پرونده جابه‌جا می‌شد؛ اگر «بازنده» می‌شد آمار Win/Loss خراب می‌شد | **انطباق:** هوک روی `offerSetSt` — وضعیت‌های won/lost برای سند `rialOf`دار مسدود است (با پیام راهنما) |
| فرصت‌های فعال | درخواست قبلاً برنده دارد → کلاً از فرصت‌ها خارج است | بدون اقدام |
| سقف اعتبار مشتری | تبدیل همان معامله است، تعهد جدیدی ایجاد نمی‌کند | عمداً از مسیر `offerSave` (و هشدار سقف اعتبار آن) عبور نمی‌کند |
| یادآور انقضای پیشنهاد | نسخه همراه سند مستقلی برای مذاکره نیست | بدون `validUntil` ساخته می‌شود |
| پیش‌پرداخت / خرید واقعی / هزینه‌ها / موتور سود | همگی به inqNo/پرونده متصل‌اند، نه به شماره پیشنهاد | بدون تغییر |
| تطبیق خرید (lineId) | کپی lineId سند ارزی می‌توانست هویت ردیف را بین دو سند مخدوش کند | lineIdها برای نسخه ریالی بازتولید می‌شوند |
| همگام‌سازی/پشتیبان | `ptf_crm_offers` و `ptf_crm_deals` از قبل در SYNC_KEYS هستند | بدون اقدام — رکورد جدید مثل هر پیشنهاد دیگری sync می‌شود |

## ۵) تست‌ها

`/tmp/test-rial-convert.js` (خارج از مخزن) — محیط شبیه‌سازی‌شده CRM، **۳۷/۳۷ قبول**:
ساخت نسخه ریالی با نرخ/تاریخ دلخواه، عدم تغییر پیشنهاد اصلی، قفل تبدیل مجدد،
بازتولید lineId، عدم کپی فیلدهای مالی/بردی، محافظ وضعیت (block برنده/بازنده، مجاز بودن سایر وضعیت‌ها)،
رد پیشنهادهای ریالی/صفر، fallback تاریخ به تاریخ پیشنهاد اولیه، تبدیل‌پذیری پیشنهاد ارزی **غیربرنده** (آمادگی فاز ۲)،
رفتار دکمه/بج نوار پرونده در هر سه حالت.

## ۶) برنامه فاز ۲ (تعمیم به همه پیشنهادهای ارزی)

هسته از همین حالا مستقل از پرونده فروش است:

- `ptfOfferRialConvertCheck(no)` / `ptfOfferRialConvertCommit(no, rate, dateISO, cb)` / `ptfOfferRialConvertOpenByNo(no)`
  روی **هر** CO/TC ارزی (برنده یا غیربرنده) کار می‌کنند.
- اقدام باقی‌مانده فاز ۲ فقط «نمایش دکمه» در ماژول پیشنهادهاست:
  افزودن `ptfOfferRialConvertOpenByNo(...)` به ردیف عملیات جدول CO در `offers.js → renderOffers`
  (و در صورت نیاز تب فرصت‌ها) + نمایش بج `ptfRialCompanionBadge` در همان جدول.
- نکته سیاستی فاز ۲: برای پیشنهاد غیربرنده، وضعیت نسخه ریالی همچنان `sent` می‌ماند؛
  اگر کاربر بعداً پیشنهاد ارزی اصلی را برنده کند، نسخه ریالی صرفاً سند همراه پرونده خواهد بود
  (هیچ‌گاه won نمی‌شود — همان هوک فعلی).
