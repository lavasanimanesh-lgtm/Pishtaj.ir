## ۲) معماری
```
مرورگر (کلاینت نازک)
  ├── getData/setData → (هوک client-server.js)
  │     ├── فاز B فعال؟  بله → سرور (data_pull/data_push) + کش محلی ۳۰ثانیه
  │     └── فاز B غیرفعال؟ → رفتار قبلی (localStorage)
  ├── آفلاین: صف ptf_b_queue + کش محلی؛ با اتصال → flush خودکار

سرور (MySQL) = منبع حقیقت
```

## ۴) گام‌های تست پیش از مرج
1. فعال‌سازی روی استیجینگ → هم‌گرایی یک‌باره → کارکرد عادی (ثبت/ویرایش/گزارش) ۲-۳ روز

- **ریسک:** خواندن از سرور در هر getData → کندی/بار سرور → کنترل: کش ۳۰ ثانیه + data_pull تکی

- **سوییچ‌بک:** دکمهٔ «غیرفعال‌سازی» → رفتار قبلی فوری

## ۶) الحاقیه v33.19.0 — رفع باگ هم‌گرایی (گزارش کاربر)

**علائم:** هم‌گرایی fail می‌شد ولی «تست اتصال» سبز بود؛ badge زرد؛ دستگاه‌های ۷۰-۹۰٪ استورج هم fail.

**ریشه‌ها و رفع:**
1. **`data_push` توکن الزامی دارد؛ `users_get` عمومی است** → تست اتصال همیشه سبز ولی ارسال fail. رفع: `serverPush` چک نیازورود (`needLogin`/`401`/regex روی error) → `ptfSyncRefreshAuth()` + یک بار retry (الگوی F0-3 backup.js)؛ در غیر این صورت پیام دقیق «نشست منقضی؛ دوباره وارد شوید».
2. **payload یک‌جا چند MB** روی دستگاه‌های پرحافظه. رفع: `ptfBPushBatch` — دسته‌های ≤۲۰ کلید؛ شکست یک دسته فقط همان را در صف نگه می‌دارد؛ needLogin → توقف کامل.
3. **نشانگر موفقیت `ptf_b_synced_<user>`** فقط پس از موفقیت کامل ارسال دسته‌ای ست می‌شود (نه قبل از ارسال) — پیش‌نیاز پاک‌سازی کش.
4. **`ptfBClearLocalCache` (جدید):** آزادسازی واقعی حافظه پس از مهاجرت. گاردها: فاز B فعال + synced + صف خالی + تایپ «پاک». داده روی سرور است؛ کش با خواندن بعدی دوباره پر می‌شود.
5. **گارد `__ptfB`:** جلوگیری از دوباره‌هوک‌شدن getData/setData (boot + ptfBEnable).

**جریان کاربر برای دستگاه پرحافظه:** رفرش → (ورود مجدد در صورت انقضای نشست) → 🔄 هم‌گرایی دادهٔ محلی → 🗑 پاک‌سازی کش محلی → تایپ «پاک».
