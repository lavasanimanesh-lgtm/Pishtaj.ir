**نسخه:** v33.18.0 — **تاریخ:** ۱۴۰۵/۰۸/۱۱
**وضعیت:** 🟢 پیاده‌سازی شد (client-server.js) — در انتظار تست استیجینگ قبل از مرج

## ۱) تصمیمات کارفرما (ثبت‌شده)
| موضوع | تصمیم |
|---|---|
| آفلاین | **صف محلی + همگام‌سازی مجدد خودکار** (تغییرات می‌ماند؛ با برگشت اینترنت push می‌شود) |
| هم‌گرایی دادهٔ محلی | **انتقال یک‌باره با تأیید کاربر** (اولین ورود پس از فعال‌سازی) |
| دامنه | **همهٔ کلیدها (فاز B کامل)** |
| مرج | **تا پایان فاز B مرج انجام نمی‌شود** (تصمیم کارفرما) |

## ۲) معماری
```
مرورگر (کلاینت نازک)
  ├── getData/setData → (هوک client-server.js)
  │     ├── فاز B فعال؟  بله → سرور (data_pull/data_push) + کش محلی ۳۰ثانیه
  │     └── فاز B غیرفعال؟ → رفتار قبلی (localStorage)
  ├── آفلاین: صف ptf_b_queue + کش محلی؛ با اتصال → flush خودکار
  └── هم‌گرایی یک‌باره: ptf_b_flushed_<user> — مودال تأیید → دادهٔ محلی → سرور
سرور (MySQL) = منبع حقیقت
```

## ۳) فایل‌ها
- `crm/client-server.js` (جدید) — هوک getData/setData + صف + flush + هم‌گرایی + فعال/غیرفعال‌سازی
- `crm/backup.js` — دکمه‌های «حالت سرور-محور» در تنظیمات
- `crm/index.html` — لود client-server.js بعد از sync.js
- `_tools/uat/tester298-phase-b.js` — ۸ تست

## ۴) گام‌های تست پیش از مرج
1. فعال‌سازی روی استیجینگ → هم‌گرایی یک‌باره → کارکرد عادی (ثبت/ویرایش/گزارش) ۲-۳ روز
2. قطع اینترنت (DevTools → Offline) → ثبت تغییر → صف → برگشت اتصال → push خودکار
3. بررسی «پاک‌سازی امن» دیگر ضروری نیست (localStorage فقط کش)
4. رگرسیون کامل + audit
5. سپس مرج → deploy پروداکشن → فعال‌سازی برای کاربران (دکمه در تنظیمات یا rollout تدریجی)

## ۵) ریسک‌ها و کنترل‌ها
- **ریسک:** خواندن از سرور در هر getData → کندی/بار سرور → کنترل: کش ۳۰ ثانیه + data_pull تکی
- **ریسک:** نوشتن همزمان → کنترل: صف + debounce + data_push موجود (server-authoritative)
- **ریسک:** دادهٔ محلی کاربر گم نشود → هم‌گرایی با تأیید + هرگز حذف نمی‌کنیم
- **سوییچ‌بک:** دکمهٔ «غیرفعال‌سازی» → رفتار قبلی فوری
