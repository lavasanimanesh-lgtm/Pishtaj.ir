## ۱) UR-11 — گزارش تنخواه «بازه‌ای» (از آخرین ارجاع تا تاریخ انتخابی)

### نیاز کاربر (ثبت‌شده)
- گزارش دورهٔ جاری باید **بازه** داشته باشد: «از زمان آخرین ارجاع تا زمانی که کاربر انتخاب می‌کند».
- پس از ارجاع هر دوره، **گزارش + منضمات همان جا به‌عنوان فیلد باقی می‌ماند** و بعداً هم قابل مراجعه است.
- دورهٔ جدید **از روز پس از آخرین ارجاع** تا هر تاریخی که کاربر انتخاب کند گزارش می‌دهد.
- قالب گزارش: «تنخواه‌گردان از تاریخ … تا تاریخ …» + ردیف هزینه‌ها/شارژها با **نام ثبت‌کننده** و **نحوهٔ پرداخت** (مستقیم از تنخواه / تسویه در فلان تاریخ توسط تنخواه‌گردان / در انتظار تسویه).
- **PDF منضمات در هر زمان قابل دریافت است.**

### معماری
| مفهوم | طراحی |
|---|---|
| کلید دوره | هر دوره = بازهٔ `[from, to]` (تاریخ شمسی `1405/MM/DD`)؛ برای سازگاری `month` هم ذخیره می‌شود |
| بازهٔ پیشنهادی | `ptfPettySuggestedRange()`: `from = روز پس از «to» آخرین دورهٔ ارجاع‌شده`، `to = امروز` (قابل تغییر توسط کاربر)؛ اگر دوره‌ای نبود → اول ماه جاری |
| فیلتر داده | `ptfPettyPeriodData(from, to)`: فیلتر `recDate(x) ∈ [from,to]`؛ بدون from/to → fallback به ماه (رفتار قبلی) |
| قالب | `ptfPettyRangeLabel` = «تنخواه‌گردان از تاریخ X تا تاریخ Y»؛ جدول: ردیف/تاریخ/نوع/شرح/توسط/**نحوهٔ پرداخت و وضعیت**/مبلغ |
| وضعیت هر هزینه | `payMode==='direct'` → «پرداخت مستقیم از تنخواه»؛ `st==='settled'` → «تسویه در {تاریخ} توسط {نام}»؛ `void` → «ابطال‌شده»؛ غیره → «در انتظار تسویه»؛ شارژها → «شارژ حساب» |
| ماندگاری گزارش/منضمات | رکورد دوره (`ptf_crm_petty_periods`) شامل `from/to/pettyIds/txIds/files` است؛ دکمه‌های «📊 گزارش دوره» و «📎 PDF تلفیقی» در فهرست دوره‌ها برای **هر دوره** (قدیم و جدید) — گزارش و رسیدها از **همان اسناد لحظهٔ ارجاع** (`pettyIds/txIds`) ساخته می‌شوند نه از دادهٔ زنده |
| PDF تلفیقی | صفحهٔ ۱ گزارش (با هدر بازه) + صفحهٔ ۲ رسیدها (۳-در-صفحه با شناسهٔ «سند N») + صفحهٔ پیوست بانک دوره |
| ارجاع دوره | `pettyClosePeriod`: فیلدهای «از تاریخ» (پیشنهادی = روز پس از آخرین ارجاع) و «تا تاریخ» + ذخیره در رکورد؛ **الزام پیوست بانک**: اگر آخرین دورهٔ ارجاع‌شده بدون پیوست باشد، ارجاع جدید مسدود می‌شود (چون دورهٔ جدید از روز پس از آن شروع می‌شود) |

### فایل‌ها/توابع تغییرکرده
- `crm/petty.js`: `ptfPettyDayAfter`, `ptfPettySuggestedRange`, `ptfPettyPeriodKey`, `ptfPettyRangeLabel`, `ptfPettyPeriodData(a,b)`, `ptfPettyPeriodEvents(a,b)` (+وضعیت), `ptfPettyPeriodTotals(a,b)`, `Report/Csv/Print/CombinedPdfHtml/CombinedPdf(a,b)` (+ستون وضعیت و هدر بازه), `ptfPettyPeriodFiles(a,b,ids)`, `renderPeriods` (نمایش بازه), `pettyClosePeriod` (از/to + الزام پیوست آخرین دوره)
- سازگاری عقب: همهٔ توابع با `(month)` هم کار می‌کنند (دادهٔ قدیمی).

## ۲) UR-12 — ساده‌سازی مختومه‌کردن پرونده فروش

### نیاز کاربر
- «مختومه‌کردن بسیار ساده‌تر باشد؛ مثلاً پکینگ‌لیست نباید اجباری باشد یا تسویه با تامین‌کنندگان و…»

### وضعیت قبل (بررسی)
- **پکینگ‌لیست و تسویه تامین‌کننده از قبل فقط هشدار بودند** (مانع نبودند) — تنها blocker سخت «ثبت تحویل به کارفرما» بود (US-437، ضد دور زدن).

### طراحی ساده‌سازی (بدون شکستن گارد مالی)
| مورد | قبل | بعد |
|---|---|---|
| پکینگ‌لیست رسمی ناقص/غایب | هشدار | هشدار (بدون تغییر) |
| بدهی باز تامین‌کننده پرونده | هشدار | هشدار (بدون تغییر) |
| **تحویل کارفرما** | blocker سخت | blocker پیش‌فرض + **مسیر تأیید صریح**: تیک «تحویل انجام شده است (با مسئولیت ثبت‌کننده)» + دلیل → `closeOverride.deliveryConfirmed` روی رکورد ذخیره و در audit ثبت می‌شود؛ با آن، blocker به هشدار تبدیل و مختومه ممکن می‌شود |
| مطالبات باز مشتری | نیازمند تیک «تسویه» | بدون تغییر (مالی مهم — حفظ شد) |

### فایل‌ها
- `crm/salesfiles.js`: `sfCloseAudit` (مسیر override)، `sfCloseModal` (چک‌باکس + دلیل + دکمهٔ فعال‌شونده)، `sfCloseGo` (ذخیرهٔ `closeOverride` قبل از commit). گارد `sfCloseSettledCommit` (blockers → return false) دست‌نخورده ماند.
