## ۱) منشأ این سند

کارفرما اعلام کرد «قرار بود به MySQL هم مهاجرت داشته باشیم». جستجوی کامل در مخزن (همهٔ برنچ‌ها، کل تاریخچه، تمام انواع فایل) نتیجه داد:

- کلمهٔ `mysql` / `mariadb` در هیچ فایل یا کامیتی **وجود ندارد** (۰ مورد).
- هیچ بک‌لاگ/سند/یادداشت تحویلی به مهاجرت دیتابیس اشاره نکرده است.

یعنی این برنامه قبلاً **فقط در گفتگو** مطرح شده و هیچ‌جا مستند نشده بود. طبق قاعدهٔ این پروژه («هر تصمیم باید مستند شود»)، این سند برای ثبت رسمی و ردیابی آن ایجاد شد.

## ۲) وضعیت فعلی معماری ذخیره‌سازی (راستی‌آزمایی‌شده — مبنای تصمیم)

| لایه | فناوری | محل | نکات کلیدی |
|---|---|---|---|
| کلاینت | `localStorage` مرورگر | `crm/index.html` (`getData`/`setData`) | منبع حقیقت اولیهٔ داده‌ها؛ کلیدهای `ptf_crm_*` (۴۸+ کلید)؛ هشدار خطای ذخیره از v33.2.x برنچ فعلی |
| سرور — دادهٔ همگام‌شده | **فایل JSON** | `api/crm.php` → `data/ptf_crm_<key>.json` | نوشتن با `file_put_contents(...LOCK_EX)`؛ به‌ازای هر کلید یک فایل؛ بدون تراکنش/ایندکس/جستجوی رابطه‌ای |
| سرور — دادهٔ جانبی | فایل JSON | `data/otp.json`، `data/ratelimit.json`، `data/counters.json`، `data/sync/ptf_crm_users.json` | OTP، محدودیت نرخ، شمارنده‌ها، کاربران همگام |
| سرور — فایل‌های ضمیمه | آروان‌کلود S3 | `api/storage.php` | Signature V4 بدون SDK؛ مستقل از بحث دیتابیس |
| احراز هویت | JWT + نقش | `api/auth.php`، `api/crm.php` | مستقل از لایهٔ ذخیره‌سازی |
| همگام‌سازی | pull/push هر کلید + merge هوشمند سمت سرور | `crm/sync.js` + `api/crm.php` | `ptfSmartMerge`؛ از جولای ۲۰۲۶ باگ‌های جدی merge (AUD-01/02/03) رفع شده‌اند |

**خلاصه:** سیستم امروز «اول کلاینت، بعد سرور» است (localStorage منبع حقیقت + JSON سرور به‌عنوان همگام‌سازی و بکاپ). هیچ لایهٔ SQL در هیچ‌جای کد وجود ندارد — بنابراین «مهاجرت به MySQL» یعنی **معماری جدید برای لایهٔ سرور (و احتمالاً کلاینت)**، نه انتقال سادهٔ یک دیتابیس موجود.

## ۳) محرک‌ها و ریسک‌های فعلی (برای وزن‌دهی به تصمیم)

1. **همزمانی/داده‌ازدست‌دادن:** فایل‌های JSON با `LOCK_EX` فقط سریال‌سازی می‌کنند؛ تراکنش و قفل رکوردی ندارند. حادثهٔ واقعی AUD-01 (گم‌شدن بی‌صدای پرداخت تامین‌کننده در تعارض sync) ریشه در همین لایه داشت (حالا رفع شده، ولی معماری همچنان شکننده است).
2. **پرس‌وجوی رابطه‌ای صفر:** گزارش‌های مدیریتی (مثل `ledger-report.js`) همه‌چیز را سمت کلاینت از حافظهٔ محلی جمع می‌زنند؛ با MySQL می‌توان گزارش‌ها/جستجو را سمت سرور برد.
3. **بکاپ/بازیابی:** بکاپ امروز = tar از `crm/data/` (آیتم `INC-A4-OFFSITE-BACKUP` هنوز باز است). دیتابیس نقطهٔ بازگشت و یکپارچگی بهتری می‌دهد.
4. **محدودیت localStorage:** ظرفیت ~۵MB هر کاربر؛ هشدار «ذخیره نشد» در برنچ فعلی دقیقاً برای همین اضافه شده. مهاجرت کامل (دامنهٔ C) این محدودیت را برمی‌دارد.
5. **نکتهٔ مقابل:** لایهٔ merge/همگام فعلی با ۱۷+ تستر UAT پخته شده و کار می‌کند؛ مهاجرت نباید آن را بشکند. هر طرحی باید قرارداد همگام‌سازی فعلی (کلید-محور) را حفظ یا صریحاً جایگزین کند.

## ۴) سؤالات باز — نیازمند پاسخ کارفرما (تعیین دامنه)

1. **دامنهٔ مهاجرت کدام است؟**
   - **گزینهٔ A — فقط لایهٔ سرور:** فایل‌های JSON سمت `api/crm.php` با MySQL جایگزین شوند (همان قرارداد کلید-ارزش، همان API)؛ کلاینت localStorage دست‌نخورده بماند. ریسک پایین‌ترین، اثر فوری: یکپارچگی/تراکنش/بکاپ سرور.
   - **گزینهٔ B — مهاجرت کامل:** کلاینت هم به‌جای localStorage مستقیماً از سرور (MySQL) بخواند/بنویسد؛ منبع حقیقت واحد سرور. معماری متفاوت، کار بزرگ‌تر، نیازمند بازطراحی همگام‌سازی و حالت آفلاین.
   - **گزینهٔ C — دو مرحله‌ای:** اول A (گام امن و تدریجی)، بعد در فاز جداگانه B.
2. **مقصد MySQL کجاست؟** هاست/سرور فعلی شرکت؟ سرویس ابری (آروان و…)؟ نسخهٔ MySQL/MariaDB و دسترسی (روت یا کاربر محدود)؟
3. **داده‌های موجود چه می‌شوند؟** (الف) فایل‌های JSON سرور → بارگذاری اولیه در MySQL؛ (ب) دادهٔ localStorage کاربران فعال → آیا باید یک‌بار آپلود/جذب شود یا از این پس به‌تدریج با sync همگرا شود؟ (قاعدهٔ پروژه: بدون تأیید صریح، backfill خودکار انجام نمی‌شود.)
4. **کلیدهای جانبی** (otp، ratelimit، counters، audit log) هم به MySQL بروند یا همان فایل بمانند؟
5. **اولویت زمانی:** مهاجرت بعد از تکمیل ثبات‌سازی جریان‌های مرج‌نشدهٔ CRM (بامپ نسخه → تسترها → تاریخچهٔ ادغام) انجام شود، یا موازی؟ آیا توسعهٔ مالی (که از ممیزی ۲۹ ژوئیه معلق است) با این کار باز می‌شود یا نه؟
6. **سقف کار:** آیا مهاجرت فقط «ذخیره‌سازی» است، یا انتظار قابلیت‌های جدید (گزارش‌های سرور، جستجو، داشبورد تحلیلی) هم در همین طرح است؟
