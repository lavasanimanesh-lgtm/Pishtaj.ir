## ۳) معماری هدف (پس از فاز B)

```
مرورگر کاربر (کلاینت نازک)
  ├── localStorage  → فقط کش/آفلاین (صف تغییرات، نه منبع حقیقت)
  └── API (crm.php) → MySQL ابری  ← منبع حقیقت واحد
                        ├── جداول دادهٔ کسب‌وکار (کلید-ارزش یا رابطه‌ای، با تراکنش)
                        ├── users / sessions / audit
                        └── بکاپ روزانه + بازیابی نقطه‌ای
```

- همگام‌سازی چندکاربره: سرور-authoritative؛ merge سمت سرور با قفل رکورد/تراکنش (جایگزین LOCK_EX روی فایل).
- گزارش‌های سنگین (مثل ledger-report) می‌توانند بعداً به سمت سرور بروند — خارج از دامنهٔ حداقلی، در فهرست «بهبودهای بعدی».

## ۷) کنترل‌های «بدون از دست رفتن داده»

1. **بارگذاری اولیه:** checksum (SHA-256) و شمارش رکورد هر کلید قبل/بعد — مغایرت = توقف خودکار.
2. **Dual-write (فاز A):** هر نوشتن هم‌زمان به JSON و MySQL تا لحظهٔ سوییچ؛ سوییچ‌بک یک‌دستوری.
3. **بکاپ:** روزانه + point-in-time؛ تست بازیابی واقعی قبل از هر سوییچ.
4. **هرگز حذف نمی‌کنیم:** JSONها و localStorage قدیمی تا پایان فاز B (و یک بازهٔ انتظار پس از آن) دست‌نخورده نگه داشته می‌شوند.
5. **تسترهای دائمی:** هر گام یک تستر Node.js (الگوی tester168) + رگرسیون sync کامل.

**تغییرات نسبت به طرح اولیه:**
- مقصد: دیتابیس ساخته‌شده در **همان سی‌پنل (MySQL Database Wizard)** به‌جای ابری جداگانه — بدون نیاز به SSH/ترمینال.
