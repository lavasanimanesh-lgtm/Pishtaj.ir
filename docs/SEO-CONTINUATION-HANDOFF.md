# سند تحویل و ادامه تقویت صفحات موجود

آخرین به‌روزرسانی: ۲۰۲۶-۰۹-۲۰ — پس از تقویت صفحه رادار سطح.

> نقطه شروع ایجنت بعدی همین سند است. ابتدا وضعیت واقعی فایل‌ها و Git را بررسی کنید؛ گزارش‌ها، ادعا درباره انتشار یا بهبود رتبه نیستند.

## ۱. خواسته و محدودیت‌های کاربر

- دستور فعال: **«صفحات مشابه نساز؛ فقط صفحات فعلی را برای سئوی بهتر تقویت کن.»**
- کیفیت، صحت فنی و کاهش ریسک سئو بر تعداد صفحات اولویت دارد. تضمین رتبه یا بی‌ریسک‌بودن ندهید.
- هدر و فوتر صفحات عمومی باید مبتنی بر صفحه اصلی و مشترک بمانند. تغییر محتوایی نباید این یکپارچگی را بشکند.
- درخواست قدیمی تولید ۵۰۰ محصول/صفحه در حال اجرا نیست. پژوهش قیمت قبلی آرشیو شده است؛ با پیام‌های کوتاه «بریم بعدی» آن برنامه را دوباره فعال نکنید.
- قیمت، موجودی، زمان تحویل، گواهی، امتیاز یا Offer ساختگی نسازید. اشاره به برند به معنی نمایندگی یا موجودی نیست.
- اگر کاربر صریحاً پژوهش قیمت را از سر گرفت: فقط کالای نو، مدل و قیمت خارجی قابل تأیید، نرخ فروش آزاد قابل استناد با زمان، محاسبه به تومان و عنوان «برآورد قیمت تأمین»؛ اعتبار و نیاز به استعلام نهایی روشن باشد. داده قدیمی را قیمت روز معرفی نکنید.

## ۴. قالب مشترک؛ منبع اصلی کجاست؟

گزارش: `docs/shared-header-footer-2026-09-19.md`

راهنمای فنی: `_tools/site-shell/README.md`

- قالب‌ها: `_tools/site-shell/header-<lang>.html.inc` و `footer-<lang>.html.inc`.
- هشت زبان موجود: fa، en، ar، de، fr، ru، tr، zh. متن و جهت محلی حفظ می‌شوند.
- استایل پایه محدود به هدر/فوتر: `_tools/site-shell/home-shell-base.css`؛ اصلاحات عمدی در `overrides.css`.
- خروجی استایل: `assets/css/site-shell.css`.
- رفتار مشترک: `assets/js/site-shell.js`؛ منوی محصول/زبان همچنان از `ptf-discover.js` هم استفاده می‌کند.
- تولید HTML ایستا: `python tools/sync_site_shell.py`؛ کنترل: همان دستور با `--check`.
- **هدر/فوتر یک صفحه را جداگانه ویرایش نکنید.** تغییر مشترک باید از منبع قالب و مولد عبور کند.
- متادیتا، مقاله، فرم و CTA خارج از دامنه تغییر قالب‌اند.
- CRM، فایل‌های داخلی و ۴۶ صفحه انتقال/ادغام از مهاجرت قالب کنار گذاشته شده‌اند؛ آن‌ها را با صفحات عمومی فعال یکسان فرض نکنید.
- فایل‌های جدید/تغییرکرده CSS و JS باید همراه HTML و نسخه URL مناسب منتشر شوند؛ کش سایت می‌تواند فایل‌های ایستا را طولانی نگه دارد.

### هش‌های حفاظت و اصلاح محتوای بعدی

`_tools/site-shell/preservation.json` مدرک تاریخی مهاجرت قالب است؛ **برای عبور دادن تست‌ها آن را بازتولید نکنید**.

وقتی محتوای یک صفحه عمداً تقویت می‌شود، فقط همان صفحه در `content-revisions.json` با موارد زیر ثبت/به‌روزرسانی شود:

- هش SHA-256 متن پس از `strip_shell` از `tools/sync_site_shell.py`؛
- تاریخ واقعی تغییر؛
- دلیل مشخص؛
- مسیر گزارش موجود.

این کار به معنی تغییر مجاز محتواست، نه حذف تست. تست‌های قالب باید همچنان برابری با قالب‌های مشترک، پوشش صفحات، شناسه‌ها و تکرارپذیری تولید را کنترل کنند. برای صفحات آینده گزارش‌های بازنگری را حفظ کنید تا سابقه تصمیم‌ها از بین نرود.

## ۵. روند اجرای مرحله بعد

1. `git status --short` و شاخه را بررسی کنید؛ تغییرات قبلی را پاک یا بازنشانی نکنید.
2. یک صفحه یا خوشه کوچک **از صفحات موجود و انجام‌نشده** انتخاب کنید. قبل از انتخاب، فایل و محتوایش را بخوانید؛ عنوان عمومی به‌تنهایی معیار اولویت نیست. انتخاب مرحله بعد هنوز قطعی نشده است.
3. دامنه را کوتاه به کاربر بگویید. در ادامه خوشه سطح، ابتدا وجود و کیفیت صفحات هم‌موضوع را بررسی کنید؛ از روی حدس فایل جدید نسازید.
4. از فایل فعلی، هدر/فوتر، H1، canonical، hreflang، robots، شناسه‌ها، تصاویر، لینک‌ها، CTA و JSON-LD فهرست بگیرید. نسخه پیش از تغییر را برای مقایسه نگه دارید.
5. منابع اولیه سازندگان/استانداردها را مستقیماً بخوانید. نتیجه جستجو به‌تنهایی تأیید متن صفحه یا نسخه سند نیست. redirect به جستجو یا صفحه 404 را منبع فنی معتبر حساب نکنید.
6. معرفی و راهنمای انتخاب را اختصاصی کنید؛ متن‌های تکراری و جدول‌های داخلی مانند «خوشه سئو/مسیر تبدیل» حذف شوند. مطالب فنی مفید، تصاویر و لینک‌های قبلی بی‌دلیل حذف نشوند.
7. تعمیم‌های خطرناک را اصلاح کنید: ویژگی یک مدل، عدد دقت، حدود دما/فشار، نیاز به متعلقات، یا ادعای ایمنی را به همه محصولات نسبت ندهید. توصیه نصب تابع دیتاشیت، طراحی و روش مصوب باشد.
8. اطلاعات RFQ، معیار مقایسه پیشنهاد و عوامل هزینه را روشن کنید. جدول‌های جدید `caption` و `scope` داشته باشند و CSS آن‌ها محدود به همان بخش باشد.
9. عنوان و توضیحات meta/OG/Twitter هماهنگ باشند. H1 و نشانی اصلی فعلاً حفظ شوند. FAQ فقط از متن قابل مشاهده ساخته شود؛ الگوی مراحل اخیر چهار سؤال است، نه سهمیه اجباری برای هر صفحه.
10. در Service شرکت را provider معرفی کنید، نه برند سازنده. Organization و breadcrumb معتبر حفظ شوند؛ امتیاز یا Offer بی‌پشتوانه اضافه نکنید.
11. فقط lastmod URL واقعاً تغییرکرده و تاریخ sitemap مربوط را به‌روزرسانی کنید؛ مجموعه URLها، redirects و robots بدون دلیل مستقل تغییر نکنند.
12. تست رگرسیون مخصوص صفحه/خوشه اضافه کنید. در تست تجمعی sitemap، اسلاگ جدید را به فهرست انتظار اضافه کنید، **نه به `SLUGS` اصلیِ تست محتوای مرحله اول**.
13. گزارش و بازنگری هش مجاز را ثبت کنید؛ کل تست‌ها، ممیزی و بررسی diff را اجرا کنید. تست موفق را فقط پس از نتیجه واقعی اعلام کنید.
14. در صورت دسترسی، مرورگر در موبایل و دسکتاپ؛ وجود H1، جدول‌ها، نبود اسکرول افقی، منوی موبایل و Escape، خطای JS و لینک RFQ بررسی شود. بدون نیاز فرم واقعی ارسال نکنید.
15. تعداد صفحات انجام‌شده و این سند را به‌روزرسانی کنید. محدودیت‌ها و عدم انتشار را در جمع‌بندی صریح بگویید.

## ۶. فرمان‌های کنترل

از ریشه مخزن:

```sh
git status --short
git branch --show-current
PYTHONWARNINGS=ignore::ResourceWarning python -m unittest discover -s tools -p 'test_*.py'
python tools/sync_site_shell.py --check
python _tools/seo_redirect_audit.py --strict
git diff --check
```

مرورگر اختیاری برای قالب مشترک، پس از آماده‌کردن Playwright، Chromium و سرور پیش‌نمایش:

```sh
python _tools/check_site_shell_browser.py --base-url http://127.0.0.1:8000 --browser /path/to/chromium
```

این اسکریپت قالب را در مسیرهای نمونه بررسی می‌کند؛ صفحه محتوایی جدید را نیز جداگانه آزمون کنید. فایل‌های محیطی `/home/user`، venv، بسته‌های npm و مرورگر `/tmp` را وابستگی پایدار فرض نکنید. بازتولید باید بر فایل‌های داخل مخزن متکی باشد، نه اسکریپت‌های یک‌بارمصرف قبلی.

برای پیش‌نمایش طولانی‌مدت از ابزار فرایند پس‌زمینه و اتصال `0.0.0.0` استفاده شود. پیش‌نمایش استاتیک PHP/API واقعی نیست؛ فایل‌های داخلی، تنظیمات محرمانه و سورس PHP را از طریق سرور ساده عمومی نکنید. تست استاتیک را تست فرم یا CRM معرفی نکنید.

## ۷. موارد باز و خطاهای شناخته‌شده

- اولویت کوتاه‌مدت: تست مرورگر صفحه رادار پس از آماده‌سازی محیط؛ گزارش قبلی صریحاً این تست را انجام‌نشده ثبت کرده است.
- در مهاجرت قالب، یک اسکریپت inline قدیمی صفحه اصلی مربوط به بهینه‌سازی تصویر مشاهده شد که با بخشی از متن FAQ مخلوط شده و `Unexpected string` می‌دهد. این خطا مستقل از هدر/فوتر بود و اصلاح نشده است؛ جزئیات در گزارش قالب. اگر اصلاح می‌کنید، آن را کار مستقل با تست و ثبت بازنگری بدانید.
- داده GSC موجود در `_audit/GSC-SNAPSHOT-2026-08-30.csv` قدیمی است؛ از آن نتیجه بهبود فعلی یا افت فعلی نگیرید.
- ابزار ممیزی عمومی زبان‌های فرعی مشخصی را کنار می‌گذارد. عدد ۶۷۶ آن شامل ۴۶ استاب است؛ عدد ۶۵۴ مهاجرت، همه زبان‌های فعال و بدون استاب‌هاست. این دو عدد را ناسازگاری سایت تلقی نکنید.
- منابع قیمت در `_tools/pricing-research/` آرشیو پژوهش‌اند، نه پیشنهاد فروش و نه مبنای انتشار خودکار.
- استاندارد کامل خریداری‌شده عموماً بررسی نشده است. دامنه عمومی استاندارد را با تأیید انطباق یک تجهیز یا طراحی یکی نگیرید.
